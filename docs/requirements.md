# 要件定義書 - レシピ管理アプリ

## 1. アプリ概要

| 項目 | 内容 |
|---|---|
| アプリ名 | myrecipe-management（仮） |
| 目的 | 個人が自分のレシピを記録・検索できるアプリ |
| 想定ユーザー | 自分（個人利用） |
| 認証 | なし（今回のスコープ外） |

前回のタスク管理アプリと同様、無料範囲・最低限の構成で作成する。
技術スタックのみ変更し、フロントエンド: Next.js / バックエンド: Ruby on Rails (APIモード) / データベース: MySQL とする。

### 1.1 背景・目的

- 本アプリはスクールの課題として作成する、個人の学習用アプリである。
- 実務を想定した「顧客に納品するアプリ」ではなく、自分一人で使うことを前提とした「学習目的」のアプリという位置づけである。
- そのため、後述の非機能要件・スコープも学習効果と実装コストのバランスを優先して決定する。

## 3. ユースケース・操作フロー

### 3.1 想定ユーザー

- 自分（開発者本人）のみ。ログイン機能はないため、URLを知っていれば誰でも閲覧・編集できる（詳細は[4.2 セキュリティ要件](#42-セキュリティ要件)を参照）。

### 3.2 主要ユースケース

| No | ユースケース | 目的 |
|---|---|---|
| UC1 | レシピを新規登録する | 作った料理のレシピを記録する |
| UC2 | レシピ一覧から探す | 過去に登録したレシピを見返す |
| UC3 | カテゴリ・キーワードで絞り込む | 作りたい料理のジャンルから探す |

| UC6 | レシピを削除する | 不要になったレシピを整理する |

## 4. 非機能要件

### 4.1 パフォーマンス

- 明確な数値目標は設けず、目安として以下を意識する。
  - ページ表示: 体感で3秒以内に表示されること
  - 同時アクセス数: 自分一人での利用を想定し、負荷対策は行わない

### 4.2 セキュリティ要件

- 認証機能は設けず、URLを知っていれば誰でも閲覧・編集・削除ができる状態でインターネットに公開することを前提とする。
- そのリスクを踏まえ、最低限以下の対策を行う。
  - SQLインジェクション対策（Railsの標準的なORM機能を使う範囲で対応）
  - 通信のHTTPS化（デプロイ先の標準機能を利用）
  - APIキーやDB接続情報などの秘匿情報は環境変数で管理し、リポジトリに含めない
  - フロントエンド〜バックエンド間のCORS設定を必要な範囲に限定する
  - 簡易的なレート制限の導入を検討する（過度なアクセス・自動化されたスクレイピング等の抑制）
- 上記はあくまで基本的な対策であり、本格的な不正アクセス対策・監視体制までは今回のスコープに含めない。

### 4.3 可用性・データ量

- 無料枠のインフラを利用するため、「常時稼働を保証しない」ことを前提とする（スリープ・再起動・メンテナンス等により一時的にアクセスできない時間帯が発生し得る）。
- 想定データ量は個人利用の範囲（数百件程度のレシピ）とし、大量データを前提としたチューニングは行わない。

### 4.4 バックアップ・復旧

- 手動での定期的な `mysqldump` によるバックアップを行う方針とする。
- バックアップファイルはローカルPCまたはクラウドストレージ（Google Drive等）に保存する。
- 自動バックアップの仕組み（cron等によるスケジューリング）は今回のスコープ外とし、思い出したタイミングで手動実行する運用とする。

### 4.5 対応ブラウザ・デバイス

- PCブラウザ（Google Chrome最新版を主対象）での動作を想定する。
- スマートフォン等でのレスポンシブ対応は今回のスコープ外とする。

### 5.4 UI要素の振る舞い

| 要素 | 振る舞い |
|---|---|
| 検索ボタン | クリックでキーワード・カテゴリ条件を一覧に反映（ページ再読込ではなく一覧部分のみ更新） |
| 新規登録ボタン | S3画面（新規モード・空フォーム）に遷移 |
| レシピカード | クリックでS2画面（該当レシピの詳細）に遷移 |
| 編集ボタン（S2） | S3画面（編集モード・既存値が入力済みの状態）に遷移 |
| 削除ボタン（S2） | 確認ダイアログ（「本当に削除しますか？」）を表示し、OKでAPIに削除リクエスト送信後S1へ遷移 |
| 保存ボタン（S3） | 入力チェック実施後、問題なければAPIに登録/更新リクエストを送信 |
| 材料/手順の＋追加ボタン | 入力欄を1行追加する（複数行入力を想定） |

### 5.5 エラー時の表示

| ケース | 表示内容 |
|---|---|
| 必須項目未入力のまま保存 | 該当項目の直下に赤字でエラーメッセージを表示し、保存処理を中断する |
| 数値項目に不正な値（文字列等）を入力 | 該当項目にエラーメッセージを表示（例:「数値を入力してください」） |
| API通信エラー（サーバーエラー・通信断） | 画面上部に共通のエラーメッセージを表示（例:「通信エラーが発生しました。時間をおいて再度お試しください」） |
| 検索結果が0件 | 一覧部分に「該当するレシピが見つかりません」を表示 |
| 存在しないレシピIDで詳細画面にアクセス | 「レシピが見つかりません」画面を表示し、一覧へ戻る導線を用意する |

## 7. 技術選定

### 7.1 前提

- 無料枠の範囲内で構築・運用できること
- 個人が学習目的で一から手を動かして実装すること（既存コードの流用はしない）

### 7.2 技術スタックと選定理由

| レイヤー | 採用technology | 選定理由 | 検討した代替候補 |
|---|---|---|---|
| フロントエンド | Next.js | React単体より学習教材が豊富で、ルーティングやAPI通信の型が最初から整っているため、学習コストと機能実装のバランスが良い | React (CRA/Vite)、Vue.js / Nuxt.js |
| バックエンド | Ruby on Rails（APIモード） | スクールで学習した言語・フレームワークであり、CRUD+検索程度の機能ならRailsの規約に乗ることで素早く実装できる | Node.js (Express)、Django |
| データベース | MySQL | 無料枠で使えるホスティングサービスが多く、学習教材・情報量も豊富なリレーショナルDBであるため | PostgreSQL、SQLite |
| デプロイ先 | 未定（実装が一通り進んだ後に検討） | フロント・バック・DBそれぞれの無料枠の制約（スリープ仕様、DB容量上限等）を比較してから決定したいため | Vercel + Railway、Render、Fly.io など |

## 8. スコープ外（今回はやらないこと）

- 複数ユーザーでの共有機能
- 画像アップロード機能

- スマートフォン等でのレスポンシブ対応
- 自動バックアップの仕組み化（cron等によるスケジューリング）
