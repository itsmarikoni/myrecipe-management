# API設計 - レシピ管理アプリ

[要件定義書](./requirements.md) の詳細ドキュメント。
[データ設計](./database_design.md) のテーブル定義、[画面・UI要件](./screen_design.md) の画面遷移・UI要素の振る舞いを受けて作成する。

## 1. 設計方針

- バックエンドはRuby on Rails（APIモード）。レスポンス形式はJSONのみとする。
- 認証機能はスコープ外のため、エンドポイントに認可（アクセス制御）は設けない。
- URL設計はRailsの規約（RESTfulルーティング）に従い、リソースは複数形（`/recipes`, `/categories`, `/tags`）とする。
- 材料（ingredients）・手順（steps）・タグ（tag_ids）は、レシピ単体のCRUDエンドポイントに対するネストした属性として扱う（独立したCRUDエンドポイントは設けない）。
  - 理由: 画面（S3登録編集フォーム）では常にレシピ1件とその材料・手順・タグをまとめて保存するため、個別のCRUD APIを用意する必要がないため。
- カテゴリ（categories）・タグ（tags）は参照用の一覧取得エンドポイントのみ用意する（[データ設計](./database_design.md#31-categories%E3%82%AB%E3%83%86%E3%82%B4%E3%83%AA) の方針により、カテゴリの新規作成・編集・削除はアプリ画面からは行わないため）。
  - タグはレシピ編集時に自由入力で新規作成されうるため（[screen_design.md](./screen_design.md) S3参照）、レシピ保存時にタグ名から既存タグを引き当て、なければ作成する処理をサーバー側で行う（詳細は[5. タグの扱い](#5-タグの扱い)を参照）。
- 日時はISO 8601形式の文字列（例: `2026-10-12T09:00:00.000Z`）で返却する。

## 2. エンドポイント一覧

| No | メソッド | パス | 概要 | 対応ユースケース |
|---|---|---|---|---|
| E1 | GET | `/recipes` | レシピ一覧取得（カテゴリ絞り込み・キーワード検索） | UC2, UC3 |
| E2 | GET | `/recipes/:id` | レシピ詳細取得 | UC4 |
| E3 | POST | `/recipes` | レシピ新規登録 | UC1 |
| E4 | PATCH | `/recipes/:id` | レシピ更新 | UC5 |
| E5 | DELETE | `/recipes/:id` | レシピ削除 | UC6 |
| E6 | GET | `/categories` | カテゴリ一覧取得（絞り込み用セレクトボックスの選択肢） | UC3 |
| E7 | GET | `/tags` | タグ一覧取得（入力補助・サジェスト用途、将来の拡張用） | - |

## 3. 各エンドポイントの詳細

### E1. GET /recipes

レシピ一覧を取得する。カテゴリ・キーワードによる絞り込みに対応する。

**クエリパラメータ**

| パラメータ名 | 型 | 必須 | 説明 |
|---|---|---|---|
| category_id | integer | 任意 | 指定時はそのカテゴリに属するレシピのみ返す。未指定時は全件（未分類含む）返す |
| keyword | string | 任意 | 料理名（title）の部分一致（LIKE）検索 |

**レスポンス例（200 OK）**

```json
{
  "recipes": [
    {
      "id": 1,
      "title": "肉じゃが",
      "category": { "id": 1, "name": "和食" },
      "cooking_time": 30,
      "servings": 2,
      "calories": 450
    }
  ]
}
```

- 一覧ではカードUI（[screen_design.md](./screen_design.md) S1参照）に必要な項目のみ返す（材料・手順・タグ・参照元URLは詳細取得時のみ返す）。
- `category` が `null` の場合は未分類のレシピを表す。
- 該当レシピが0件の場合は `"recipes": []` を返す（200 OKのまま、エラーとしない）。

### E2. GET /recipes/:id

レシピ詳細を取得する。

**レスポンス例（200 OK）**

```json
{
  "recipe": {
    "id": 1,
    "title": "肉じゃが",
    "category": { "id": 1, "name": "和食" },
    "cooking_time": 30,
    "servings": 2,
    "calories": 450,
    "source_url": "https://example.com/recipe/123",
    "ingredients": [
      { "id": 10, "name": "じゃがいも", "quantity": "3個", "position": 0 },
      { "id": 11, "name": "牛肉", "quantity": "200g", "position": 1 }
    ],
    "steps": [
      { "id": 20, "step_number": 1, "description": "じゃがいもを乱切りにする" },
      { "id": 21, "step_number": 2, "description": "牛肉と一緒に炒める" }
    ],
    "tags": [
      { "id": 30, "name": "簡単" }
    ],
    "created_at": "2026-10-01T09:00:00.000Z",
    "updated_at": "2026-10-01T09:00:00.000Z"
  }
}
```

- 材料・手順が未登録の場合はそれぞれ空配列（`"ingredients": []` / `"steps": []`）を返し、フロント側で「未登録」表示に変換する（[screen_design.md](./screen_design.md) S2参照）。
- 存在しない`id`の場合は404を返す（[4. エラーレスポンス](#4-エラーレスポンス)参照）。

### E3. POST /recipes

レシピを新規登録する。

**リクエストボディ例**

```json
{
  "recipe": {
    "title": "肉じゃが",
    "category_id": 1,
    "cooking_time": 30,
    "servings": 2,
    "calories": 450,
    "source_url": "https://example.com/recipe/123",
    "ingredients": [
      { "name": "じゃがいも", "quantity": "3個" },
      { "name": "牛肉", "quantity": "200g" }
    ],
    "steps": [
      { "description": "じゃがいもを乱切りにする" },
      { "description": "牛肉と一緒に炒める" }
    ],
    "tag_names": ["簡単", "時短"]
  }
}
```

- `title` のみ必須。`category_id`、`cooking_time`、`servings`、`calories`、`source_url`、`ingredients`、`steps`、`tag_names` はすべて任意（省略または空配列可）。
  - 理由: 「参照元URLだけ登録し、材料・手順は後で書き足す」というブックマーク的な使い方に対応するため（[features.md](./features.md) 1.3参照）。
- `ingredients` の `position` はリクエスト配列の順序でサーバー側が自動付与する（0始まり）。
- `steps` の `step_number` はリクエスト配列の順序でサーバー側が自動付与する（1始まり）。
- `tag_names` はタグ名の文字列配列で指定する（タグIDではない）。サーバー側で既存タグとの名前一致を確認し、一致するものがなければ新規タグを作成して関連付ける（詳細は[5. タグの扱い](#5-タグの扱い)参照）。
- 成功時は201 Createdで、作成されたレシピ（E2と同形式）を返す。
- 入力チェックエラー時は422 Unprocessable Entityを返す（[4. エラーレスポンス](#4-エラーレスポンス)参照）。

### E4. PATCH /recipes/:id

レシピを更新する。リクエストボディの形式はE3と同じ。

- 材料・手順は更新リクエストに含まれる内容で全件置き換える（差分更新ではなく、既存の材料・手順をいったん削除し、リクエストの内容で作り直す）。
  - 理由: フォーム画面（S3）では材料・手順を行単位で自由に追加・削除・順序変更できるため、個々の行のID管理をフロント側に持たせるより、全件置き換えの方が実装がシンプルになるため。
- `tag_names` も同様にリクエストの内容で関連付けを全件置き換える。
- 成功時は200 OKで、更新後のレシピ（E2と同形式）を返す。
- 存在しない`id`の場合は404、入力チェックエラー時は422を返す。

### E5. DELETE /recipes/:id

レシピを削除する。関連する材料・手順・タグ関連（recipe_tags）もDBの外部キー制約（ON DELETE CASCADE）により合わせて削除される（[データ設計](./database_design.md) 3.3〜3.6参照）。

- 成功時は204 No Contentを返す（レスポンスボディなし）。
- 存在しない`id`の場合は404を返す。

### E6. GET /categories

カテゴリ一覧を取得する。一覧画面の絞り込みセレクトボックス、登録編集フォームのカテゴリ選択肢に使用する。

**レスポンス例（200 OK）**

```json
{
  "categories": [
    { "id": 1, "name": "和食" },
    { "id": 2, "name": "洋食" },
    { "id": 3, "name": "中華" },
    { "id": 4, "name": "デザート" }
  ]
}
```

- カテゴリの新規作成・編集・削除のエンドポイントは設けない（[1. 設計方針](#1-設計方針)参照）。

### E7. GET /tags

タグ一覧を取得する。

**レスポンス例（200 OK）**

```json
{
  "tags": [
    { "id": 30, "name": "簡単" },
    { "id": 31, "name": "時短" }
  ]
}
```

- 現時点のUIではタグ入力に既存タグのサジェスト機能はないため必須のエンドポイントではないが、将来的な入力補助機能のために用意する。

## 4. エラーレスポンス

共通のエラーレスポンス形式を以下の通りとする。

```json
{
  "error": {
    "message": "レシピが見つかりません",
    "details": {
      "title": ["を入力してください"]
    }
  }
}
```

| ステータスコード | 発生ケース | `details` |
|---|---|---|
| 404 Not Found | 指定した`id`のレシピが存在しない | なし |
| 422 Unprocessable Entity | 入力チェックエラー（例: `title`未入力） | 項目名をキーとしたエラーメッセージ配列（Railsの`ActiveRecord::Errors`形式を想定） |
| 500 Internal Server Error | サーバー側の想定外エラー | なし |

- フロント側では、422の`details`をフォーム各項目のエラーメッセージ表示に使用し、404・500は画面共通のエラーメッセージ表示に使用する（[screen_design.md](./screen_design.md) 5.エラー時の表示 参照）。

## 5. タグの扱い

- タグはレシピ登録・編集フォーム（S3）でカンマ区切り等による自由入力を想定しており、ユーザーは既存タグか新規タグかを意識せず入力する。
- フロントエンドはタグ名の文字列配列（`tag_names`）をリクエストに含めるのみで、タグIDの管理は行わない。
- サーバー側（Rails）は以下の処理を行う。
  1. リクエストの`tag_names`each について、`tags.name`が完全一致する既存レコードを検索する。
  2. 一致するレコードがなければ新規に`tags`レコードを作成する（`find_or_create_by`相当の処理）。
  3. 対象レシピの`recipe_tags`を、解決した`tag_id`の集合で置き換える。
- 上記方針により、タグ名の重複作成を防ぎつつ、フロント側の実装をシンプルに保つ。

## 6. 今後の検討事項

- タグによる一覧の絞り込み検索は現時点のスコープ外のため、E1にタグ条件のクエリパラメータは設けていない（将来対応する場合は追加する）。
- ページネーションは現時点では導入しない（想定データ量が数百件程度のため）。将来件数が増えた場合は`page`/`per_page`等のクエリパラメータをE1に追加する。
